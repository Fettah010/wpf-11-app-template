## 1. Delivered outcome

The Tabbed shell's document area no longer renders a pure-white panel; it uses
the themed host surface in both Dark and Light. The detail `GridSplitter` uses
the themed divider token instead of WPF's default bright paint. Both defects
are fixed at the root (a derived-type style-resolution gap), a regression test
fails on the pre-fix revision and passes after, and a deterministic
visual-verification check detects a re-introduced white surface. No new
packages, no breaking changes, and no template-surface change.

## 3. Root cause and fix

- **Root cause (proven by controlled A/B).** The Tabbed shell hosts documents
  in a WPF-UI `ui:TabView`, which is an empty
  `public class TabView : System.Windows.Controls.TabControl { }` subclass.
  WPF resolves implicit styles by exact type match, so WPF-UI's implicit
  `Style TargetType="{x:Type TabControl}"` (`Background` =
  `TabViewBackground` = transparent `#00FFFFFF`, `OverridesDefaultStyle`) is
  **not** applied to the derived `TabView`. The control therefore falls back to
  the built-in WPF `TabControl` theme template whose content border is white —
  measured at **67.859%** of a maximized Dark window.
- **Fix.** `ui:TabView` applies WPF-UI's own style explicitly
  (`Style="{StaticResource {x:Type TabControl}}"`), so the intended transparent
  themed surface (`CornerRadius 0,4,4,4`, top border) renders over the
  `#272727` NavigationView host. The `Frame` keeps `Background="Transparent"`
  (the original design intent).
- **Rejected alternatives.** (A) An explicit opaque background brush verified at
  ~0.7% white but left the built-in template chrome and introduced a `#202020`
  document-surface seam against the `#272727` chrome. (C) An app-level implicit
  `ui:TabView` style is equivalent to the chosen fix but app-wide (only one
  `TabView` exists).
- **Second defect.** The detail `GridSplitter` used the default `#F0F0F0`
  paint, a 4 px vertical band (x≈2256–2259, 1188 px tall). It now uses
  `Background="{DynamicResource AppDividerBrush}"` (`DividerStrokeColorDefault`,
  `#3A3A3A`). Token rule respected: an existing `App*` token is reused; no
  WPF-UI key is redefined.
- **Documented consequence.** The document area and the surrounding chrome share
  the same `#272727` layer (consistent with every other shell, whose pages also
  render on the NavigationView host). Tab item headers were already WPF-UI
  styled (WPF-UI's `TabView` creates base `TabItem` containers, which match the
  `Style TargetType="TabItem"` exactly).

## 5. Performance

(≤ 150 MB); startup is unchanged (no new work on the launch path).

## 6. Accessibility and visual verification

- No interaction or automation-name changes; keyboard behavior unchanged.
  Contrast improves (the white-on-dark panel is gone).
- Deterministic verification added: `eng/verify-shell-surfaces.ps1` captures the
  maximized window with `PrintWindow` (not `CopyFromScreen`, which can catch
  unpainted frames) and asserts (a) the pure-`#FFFFFF` fraction is below a
  documented threshold in Dark and (b) no bright `#F0F0F0` vertical band
  remains. Thresholds: `MaxWhitePercent` 1.0, `MaxBrightBand` 200 px.
- Fallback: if the WPF-UI `TabControl` style key ever disappears, the startup
  style reference is caught by the launch/UI gate; the explicit `App*` token
  surface remains an available mitigation (recorded in the plan).

## 7. Template / package verification

- The regression test is repository-only: `.template.config/template.json`
  excludes `tests/DevTemWpf.Unit/TabbedShellSurfaceTests.cs` alongside the other
  repo-only guards, so generated apps do not receive it.
- `eng/verify-shell-surfaces.ps1` is a repository dev tool (like
  `capture-screenshots.ps1`); it is not packaged (the pack csproj includes only
  `eng/smoke.ps1` and `eng/measure-startup.ps1`).
- Source matrix and package matrix (from `DevTemWPF.Templates.1.4.1.nupkg`) both
  PASSED, covering Clean/Recommended/Full generation, build, launch, the
