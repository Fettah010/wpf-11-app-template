# 1.8.0 migration and compatibility draft

**Status:** Draft for the 1.8.0 architecture proof; not a 2.0 migration guide.
No 1.x breaking change is intended. Finalize the supported migration steps
only after the 2.0 preview package identities and APIs are approved.

## Compatibility summary

| Surface | 1.7.0 / existing generated app | 1.8.0 generated app | 2.0 direction |
|---|---|---|---|
| Project layout | `DevTemWpf.App` plus optional tests | App project plus `DevTemWpf.UI` source project | Candidate for stable independent packages; identity/API still open |
| Design-token dictionaries | Compiled into app project under `DesignTokens/` | Compiled into `DevTemWpf.UI`; app merges referenced-assembly pack URIs | Preserve keys unless a separately approved migration maps them |
| Resource keys | `App*` keys, including `AppPageMargin` | Names and values preserved; dictionary assembly/path changes | Keep compatibility or provide explicit key migration |
| Density | App selects Comfortable/Compact at startup and when settings change | Same behavior; app replaces the library-owned spacing dictionary | App remains composition root unless a later ADR changes this |
| Shell/navigation | App-owned `MainWindow`, `NavigationRoutes`, and shell selection | Unchanged; no Windows assembly | No 2.0 move is approved by this ADR |
| DI/services | App-owned `AppComposition`; optional modules controlled by template flags | Unchanged; no service package split | No service API/package contract approved |
| Project template flags | `Preset`, `Shell`, `Custom*`, `IncludeTests` | Unchanged | Preserve through 1.x; review only in the 2.0 preview |
| Item templates | Eleven stable IDs; `--RootNamespace` and `-n` naming contract | Unchanged | Preserve or explicitly map before any breaking change |
| Settings/configuration | Existing settings JSON and typed options | Unchanged | No format change authorized |

## 1.x project behavior

The 1.8 template source adds a `DevTemWpf.UI` project and a project reference
from the app. This affects projects newly generated from the 1.8 template; it
does not rewrite existing generated projects. Existing 1.7-or-earlier apps
continue compiling their app-owned dictionaries and need no migration for
1.8.

In the 1.8 generated app, token resource dictionaries are merged from the
referenced assembly. The resource keys and expected spacing values are
unchanged. The library version `1.8.0-prototype.1` is an internal architecture
proof and must not be interpreted as a stable public control API or a promise
of independently versioned package compatibility.

```xml
<ResourceDictionary Source="pack://application:,,,/DevTemWpf.UI;component/DesignTokens/SemanticColors.xaml" />
```

The app remains responsible for resource merge order and density selection.
The WPF-UI theme/control dictionaries load before the token dictionaries.
Comfortable spacing resolves `AppPageMargin` to `24`; Compact resolves it to
`16`.

## Preserved scaffolding and app contracts

- `dotnet new devtemwpf-app` flags (`--Preset`, `--Shell`, `--Custom*`, and
  `--IncludeTests`) do not change.
- All eleven `devtemwpf-*` item-template IDs retain the 1.7 `--RootNamespace`
  and name-derived companion type behavior.
- `AppComposition`, `MainWindow`, `NavigationRoutes`, page/ViewModel
  registrations, service interfaces, optional module flags, settings files,
  and configuration sections remain app-owned and unchanged.
- The 1.8 package boundary adds no runtime dependency beyond the local UI
  project/package. It adds no Windows or service library.

## Existing app owners

No automatic 1.x migration is needed. If manually moving an existing app's
token dictionaries to the UI project, move all five compiled dictionaries
together, update the merge URI to the referenced assembly, preserve
WPF-UI-before-token merge order, and keep density selection in the app. Verify
both densities and the runtime swap. Do not copy only `SemanticColors.xaml`:
the other token dictionaries and their merged-resource dependencies are part
of the same boundary.

## 2.0 migration work still required

This draft is not sufficient for a 2.0 release. Before 2.0 preview, the
project must finalize package IDs and versioning, decide whether resource keys
are public API, test an actual 1.x-to-2.0 generated-app conversion, document
DI and service registration changes (if any), and provide a rollback path.
Any Windows/service package split requires its own independent consumer,
accepted ADR, and package canary. Do not infer or automate those migrations
from this document.
