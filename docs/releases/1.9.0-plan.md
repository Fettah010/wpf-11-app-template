## 1. Outcome and success definition

Establish the final, reproducible 1.x compatibility and quality baseline for
the first 2.0 preview. Stabilize only confirmed defects on the supported 1.x
surface, verify advertised app/template combinations from source and the
published template package, classify the deferred backlog, and document the
known 2.0 contract changes with practical migration examples.

Success means a clean clone and clean package consumer can reproduce the
documented 1.9.0 evidence; all required build, unit/integration, UI,
generator, template, dependency, license, security, and package-content gates
pass or are explicitly blocked with a reason; the required UI suites report
non-zero executed tests; no unannounced 1.x contract break is introduced;
each deferred item is dispositioned; and the 2.0 breaking-change set and
1.x-to-2.0 migration mappings are reviewed before the 2.0 preview starts.
Performance and accessibility baselines must describe actual conditions and
limitations rather than claim evidence that was not collected.

This is a stabilization and migration-preparation release, not the 2.0
conversion. The plan does not authorize new feature families, speculative
library splits, or breaking 1.x changes.

### Research interpretation

The 1.8.0 experience demonstrates why CI status, release artifacts, and branch
state must be kept distinct: the candidate was released from a pinned SHA,
while PR #16 carried subsequent reliability/documentation changes that are
now on `main`. Reproducibility requires validating both generated source and
the actual packed template; retries and success messages alone do not explain
an anomalous subprocess exit. A 2.0 migration baseline also needs a full
observable-contract inventory, not merely a list of public C# declarations.

The sources above are research leads, not a substitute for milestone
execution-time checks. Refresh SDK/runtime, package versions, vulnerability
and license findings, WPF/UI toolkit support, and relevant GitHub/CI state
when the plan is approved and again before release.

## 6. Design and architecture

- Preserve the 1.x composition structure and current `DevTemWpf.UI` token
  resource boundary. Treat the UI package as a resource-boundary proof, not
  as a stable broad public control API.
- Preserve package identities and all documented/observable template
  contracts during 1.9. Candidate 2.0 names or breaking mappings belong in
  migration documentation as proposals until their owners approve them.
- Keep application shell, Windows integration, motion policy, and optional
  service implementations in their current boundaries unless a confirmed
  defect requires the smallest correction. No new assembly split is in scope.
- Use `docs/releases/1.8.0-migration.md` as source material, but replace or
  clearly supersede its draft status with the complete reviewed compatibility
  inventory and migration examples before 1.9 completion.
- Record each defect fix with reproduction, root cause, regression test,
  affected contracts, and rollback path. Do not suppress a failing test,
  broaden skips, or weaken thresholds to create a green gate.
- Avoid public API compatibility tooling until the concrete package
  identities and baseline artifacts are selected; measure tool coverage
  against C#, XAML/resource, template, and CLI contracts separately.

## 9. Test and CI plan

Run after plan approval from a clean clone at the actual 1.9 source SHA. The
exact command-line arguments and matrix must be recorded with the results.
Existing CI runs on `windows-latest`, installs the .NET 10.0.x SDK, and
currently runs these gates:

- Restore and Release build with zero warnings:
  `dotnet restore` and `dotnet build -c Release --no-restore --warnaserror`.
  Run Debug and Release builds where the changed projects/configuration make
  both applicable.
- Full test suite:
  `dotnet test -c Release --no-build`. Record passed, failed, skipped, and
  not-run counts; do not treat an opt-in UI suite as executed.
- Required UI automation:
  `powershell -ExecutionPolicy Bypass -File eng/check-ui-tests.ps1`. The
  supported interactive Windows hosted gate must execute the required cases;
  an unavailable desktop or non-zero skip count blocks the required gate.
- Item generators:
  `powershell -ExecutionPolicy Bypass -File eng/test-generators.ps1`, both
  from source and against the packed template package where supported.
- Source template matrix:
  `powershell -ExecutionPolicy Bypass -File eng/test-templates.ps1`. Cover
  Clean/Recommended/Full; Sidebar/Rail/Top/Tabbed; every advertised module
  flag enabled/disabled; item generators; high-risk supported combinations;
  generated unit tests; build and smoke. Use isolated template registration
  and temporary output as the script provides.
- Packed template matrix:
  pack `templates/pack/DevTemWPF.Templates.csproj`, then run
  `eng/test-templates.ps1 -PackagePath <exact-nupkg>` and
  `eng/test-generators.ps1 -PackagePath <exact-nupkg>` for the exact artifact.
  Verify package file list, package README, no local paths/secrets/build
  outputs, and promised module absence.
- UI package canary:
  `powershell -ExecutionPolicy Bypass -File eng/test-ui-package.ps1`; confirm

- Relevant UI/resource surface check:
  `powershell -ExecutionPolicy Bypass -File eng/verify-shell-surfaces.ps1`

## 14. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Published 1.8 tag differs from merged main | Keep tag immutable; state both exact SHAs and validate the merged main baseline |
| A stabilization release expands into a feature release | Require every implementation task to map to §§4 and 8; defer unrelated work |
| A generated-source pass hides packed-package failure | Validate source and exact `.nupkg` independently in clean isolated consumers |
| Intermittent smoke subprocess return code obscures actual result | Preserve per-command stdout/stderr and exit status; reproduce and diagnose rather than relying only on rerun |
| A 2.0 migration example freezes an unapproved API | Mark candidate decisions explicitly; obtain owner approval before calling the contract frozen |
| Support text creates an unstaffed maintenance commitment | Require owner policy/capacity decision before publishing duration or response promise |
| CI UI test is skipped or has no interactive desktop | Require supported Windows UI runner and non-zero executed counts; block release if unavailable |
| Generated UI navigation intermittently misses a page transition | Use accessible UI Automation activation and wait for the intended page/control; keep exact generated UI suites in source and packed matrix gates |
| Older performance numbers are not comparable | Re-run on described hardware/configuration and label missing reference-machine evidence |
| Security/license/package drift appears after 1.8 | Repeat audits on exact candidate package and report actual findings |
| Cleanup deletes useful historical work | Keep historical branches and unrelated files unless exact cleanup targets are approved |
