# 1.x compatibility inventory and 2.0 migration draft

**Status:** 1.9.0 working draft; owner review required before any 2.0 public
contract is frozen. This document supersedes the 1.8.0 architecture-proof
draft as the current inventory, but it does not approve package IDs, APIs, or
breaking changes for 2.0.

## 1.x contracts to preserve

| Surface | Current 1.x contract | 2.0 disposition |
|---|---|---|
| Application and UI projects | `DevTemWpf.App` is the composition root. Since 1.8, generated apps include `DevTemWpf.UI` for five compiled design-token dictionaries. | Keep app and UI responsibilities distinct. Stable package identity and any additional package boundaries remain open. |
| XAML resources | App merges `SemanticColors.xaml`, `Typography.xaml`, `Shapes.xaml`, and one spacing dictionary from `DevTemWpf.UI`; WPF-UI theme/control dictionaries load first. `App*` keys, including `AppPageMargin`, remain app-facing. | Inventory every key and URI before changing ownership. Preserve keys or provide an approved mapping and tested replacement URI. |
| Density | App selects Comfortable or Compact spacing and replaces the spacing dictionary at runtime. `AppPageMargin` resolves to 24 or 16 respectively. | Preserve behavior; exact token/package ownership is open. |
| Window and navigation | `MainWindow`, `NavigationRoutes`, shell selection, and route registration remain app-owned. `ShellMode` supports Rail, Sidebar, Top, and Tabbed; shell selection applies after restart. Pages use `INavigableView<T>` and `INavigationAware`, with transient app registrations. | The roadmap proposes Windows adapters and module registration, but does not yet approve a new `MainWindow` API or a move of app-owned navigation. |
| Services and modules | `AppComposition` registers app-owned services. Optional modules are selected by template flags and dependency rules; they are not independent stable service packages. | Package/module split and registration APIs remain open. Keep Clean optionality and absence guarantees. |
| Template CLI | `devtemwpf-app` supports `Preset`, `Shell`, `Custom*`, and `IncludeTests`; eleven `devtemwpf-*` item IDs have stable naming/namespace behavior. | Preserve or explicitly map each ID, flag, default, generated path, and naming rule before any breaking change. |
| Settings and local data | `ShellSettings` JSON is additive: unknown fields are ignored and missing fields default. SQLite schema is app-owned. | No 2.0 format change is approved. Any future schema change needs versioned migration and rollback evidence. |
| Target framework | Projects target `net10.0-windows10.0.26100`. | Reassess the target and OS floor with clean-consumer evidence; do not silently widen or raise it. |

The machine-readable 1.x scaffold summary remains in
[`docs/frozen-surface.md`](../frozen-surface.md). The UI package boundary is
limited to compiled design-token resources by
[ADR-0020](../decisions/ADR-0020-ui-resource-package-boundary.md); it is not
a stable broad control API.

## Concrete 1.7-to-1.8 resource example

An existing 1.7 app keeps its app-owned dictionaries and needs no migration
to consume the 1.8 template package. A newly generated 1.8 app references the
UI resource assembly instead:

```xml
<ResourceDictionary Source="pack://application:,,,/DevTemWpf.UI;component/DesignTokens/SemanticColors.xaml" />
```

The same boundary applies to all five dictionaries. Keep the WPF-UI theme
and control dictionaries before the token dictionaries, and keep density
selection in the app. A manual move must update all five resource sources
together and verify both spacing modes and the runtime swap. The package
name, assembly name, and resource keys in this example are current 1.8
contracts, not a 2.0 naming decision.

## 2.0 candidate change groups and migration examples

These are migration assignments, not approved implementation decisions.
Replacement names and APIs are intentionally placeholders until the 2.0
preview package graph and public API are reviewed.

| Candidate group | 1.x before | Migration example to validate in a 2.0 canary | Decision still required |
|---|---|---|---|
| Package identities and references | App project reference to `DevTemWpf.UI`; other runtime packages are app-owned. | Replace the 1.x UI reference with the approved 2.0 UI package/reference, then restore and build without repository source paths or a gallery-app reference. | Final package IDs, versioning, and whether packages or project references are the supported path. |
| `App.xaml` resources and styling | Merge `pack://application:,,,/DevTemWpf.UI;component/DesignTokens/...`; consume `App*` token keys. | Change the assembly/package URI only if its approved name changes; map removed keys through a reviewed old-to-new table. Compare light/dark/system and Comfortable/Compact output. | Key stability, ownership, namespace, and final pack URIs. |
| `MainWindow` and Windows integration | `MainWindow` and window lifecycle/chrome are app-owned; app composition registers app services. | If Windows integration moves behind a module, replace only the approved registration seam; keep app startup/window ownership unchanged unless a separate decision requires otherwise. | Whether `MainWindow` remains app-owned and the Windows-module registration contract. |
| Navigation and controls | App-owned `NavigationRoutes`, transient page registrations, `INavigableView<T>`, and `INavigationAware`. | Port a representative page by preserving route and lifecycle behavior; update only the interfaces or registrations explicitly changed by the 2.0 API. | Which page hooks, shell contracts, controls, and properties become public library APIs. |
| Services and optional modules | `AppComposition` plus template-gated optional source, references, registrations, configuration, and tests. | Move a selected capability only to its approved module package; remove that reference and verify its files, registrations, settings, and runtime dependencies are absent. | Module boundaries, package IDs, dependency edges, and registration method names. |
| Template identity and generated layout | `dotnet new devtemwpf-app`, named presets, four shell values, Custom flags, and eleven stable item IDs. | Install the 2.0 templates side by side, generate a sibling app with equivalent preset/shell/modules, then port application code; do not expect an installed-template update to rewrite existing files. | New template IDs/flags, compatibility aliases, generated project names/paths, and conversion support. |
| Settings/database format | Additive `ShellSettings` JSON and app-owned SQLite `user_version` migrations. | Back up the 1.x profile, run an explicit versioned migration in the canary, compare settings and user data, and verify rollback from the backup. | Whether the format changes at all; if so, exact version mapping and recovery semantics. |

### Representative migration procedure

1. Keep the 1.x source tree, template package, and user-data backup unchanged.
2. Install the exact approved 2.0 preview template package in an isolated CLI
   home and generate a sibling app with equivalent preset, shell, and optional
   modules.
3. Migrate one surface at a time: project/package references, XAML resources,
   window and navigation composition, services, then generated pages and
   controls. Use the approved API mapping; do not infer replacements from
   prototype names.
4. Build and test the sibling app without a reference to repository source or
   the gallery. Exercise startup/shutdown, navigation, themes, density,
   optional-module absence, and settings/data migration.
5. Keep the original 1.x app available until the canary passes. Roll back by
   restoring its project references and files and restoring the pre-migration
   user-data backup; do not downgrade a migrated database in place unless a
   tested reverse migration exists.

For template upgrades, `dotnet new` creates projects; it does not rewrite
existing generated apps. Record the exact old and new template package
versions, generate a fresh side-by-side scaffold, and port changes
deliberately. A future automatic converter requires its own approved plan and
representative canaries.

## Owner review required before 2.0 preview

- Approve the package/project graph, IDs, versioning, and supported consumer
  path.
- Decide which resource keys, controls, page hooks, shell contracts, and
  module registrations are public and supported.
- Approve template IDs/flags, aliases, defaults, project naming, and generated
  file layout.
- Decide whether settings or local-data formats change and approve migration
  and rollback behavior.
- Review every old/new example against the actual 2.0 preview canaries.

Until those decisions are recorded, candidate rows above are not promises of
2.0 behavior and must not be used to implement a 2.0 conversion.
