## 1. Outcome and success definition

New pages, controls, ViewModels, services, and tests can be generated
consistently, quickly, and with fewer developer/code-agent mistakes.
Success = `dotnet new` item templates exist for all standard application
elements (standard page, settings page, list-detail page, datagrid page,
treeview page, tabbed workspace page, custom control, standalone ViewModel,
service, and companion test scaffolds); each template compiles without manual
repair when generated into a scaffolded app; generated tests assert real
behavior; a decision on Visual Studio integration is recorded with evidence
(ADR-0019); generated README/FEATURES/scaffold documentation is clear and
accurate; and an automated generator smoke script (`eng/test-generators.ps1`)
validates deterministic generation across multiple namespace and naming
permutations with zero unresolved template tokens.

## 3. Research questions, evidence, and analysis

### 3.1 Item template catalog & generator architecture

| | |
|---|---|
| **Question** | What item templates provide real value, and how should symbols/namespaces be substituted? |
| **Options** | (A) Monolithic parameter-heavy generator; (B) Focused, single-purpose item templates with consistent conventions; (C) Minimal additions |
| **Evidence** | Developers and coding agents commonly need standard UI patterns: Settings, List/Detail, DataGrid, TreeView, Tab document, and Custom Control. The .NET template engine (`template.json`) excels at single-purpose templates where `sourceName` replaces the item name and `symbols.Namespace` replaces the target project namespace. |
| **Finding** | Focused templates (option B) with standardized naming (`devtemwpf-<item>`) are easiest to discover, script, and validate without complex conditional syntax. |
| **Decision** | Implement 8 new/refined item templates in `templates/items/`: `devtemwpf-page`, `devtemwpf-settings`, `devtemwpf-listdetail`, `devtemwpf-datagrid`, `devtemwpf-treeview`, `devtemwpf-tabpage`, `devtemwpf-control`, `devtemwpf-viewmodel`, `devtemwpf-service`, and test scaffolds `devtemwpf-test-vm` and `devtemwpf-test-service`. |

### 3.2 Visual Studio integration (D08r)

| | |
|---|---|
| **Question** | Should we build a dedicated VSIX extension or rely on CLI-first `.template.config` integration? |
| **Options** | (A) Build and ship a Visual Studio extension (VSIX); (B) CLI-first templates with native Visual Studio 2022/2026 template discovery |
| **Evidence** | Modern Visual Studio (2022 v17.4+ and 2026) natively discovers installed `dotnet new` templates in both the **New Project** and **Add -> New Item** dialogs when templates define `classifications: ["Desktop", "WPF", "MVVM"]` and `tags: { "type": "item" }`. Building a VSIX requires `Microsoft.VSSDK.BuildTools`, separate signing certs, VS-version compatibility shims (32-bit vs 64-bit), Marketplace publishing, and continuous clean-environment testing. |
| **Finding** | A dedicated VSIX adds immense maintenance overhead without adding capability beyond what `dotnet new install` and Visual Studio's native template engine already provide. |
| **Decision** | (B) CLI-first architecture with documented Visual Studio native discovery. Record decision in ADR-0019. |

### 3.3 Repeatable generator verification script

| | |
|---|---|
| **Question** | How to reliably assert that every item template generates valid code and tests? |
| **Options** | (A) Ad-hoc manual verification; (B) Automated verification script `eng/test-generators.ps1` that generates a sample app, adds each item template, builds with `--warnaserror`, runs tests, and asserts zero unsubstituted template tokens. |
| **Decision** | (B) Automated script `eng/test-generators.ps1`, integrated into testing workflows and runnable in CI/local gates. |

## 6. Design and architecture

- Each item template resides in `templates/items/<shortName>/` with its own `.template.config/template.json`.
- Standard symbols:
  - `sourceName`: Replaced with the user-specified name (e.g., `SamplePage` -> `CustomerPage`).
  - `RootNamespace`: Default `DevTemWpf`, replaces the whole `DevTemWpf` root so both
    `<Root>.App` and `<Root>.Unit` resolve from one value.
  - Companion names: template `forms` with `"identifier": "replace"` derive the
    secondary types from `-n` (`OrdersPage` -> `OrdersRow`/`OrdersItem`/`OrdersNode`,
    `AuditServiceTests` -> `AuditService`).
- Generated code adheres strictly to project standards:
  - C# 13 / .NET 10 nullable enabled, file-scoped namespaces, implicit usings.
  - XAML tokens: Uses static resources from `Resources/Tokens/` rather than hardcoded metrics or hex colors.
  - ViewModel: Inherits from `ObservableObject`, uses `[ObservableProperty]` and `[RelayCommand]`.
  - Views implement `INavigableView<T>` where navigation-aware.
  - Wire entrance motion via `IMotionService.PlayEntranceAsync(this)`.

### 6.1 Mid-version clarification (recorded 2026-10-27)

Discovery: the planned `Namespace` symbol (default `DevTemWpf.App`) cannot serve
the test scaffolds, which live in `DevTemWpf.Unit`; it also left companion model
types (`SampleDataGridRow`, `SampleTreeNode`, `SampleListItem`, `SampleViewModel`,
`SampleService`) unrenamed, so a second generation into the same project collided
on both the class and the file name. Impact: one symbol replacement
(`RootNamespace` over `DevTemWpf`) plus `forms`-derived companion names; companion
files are named `<SourceName>.Row.cs` / `.Item.cs` / `.Node.cs` because `replaces`
rewrites content but not file names. Tasks T03-T12, the generator gate, and
AC03 wording are updated accordingly; scope, acceptance criteria, and the
roadmap requirement are unchanged.

## 10. Performance plan and budgets

- Scaffolding templates must not increase runtime footprint or startup time of the main template.
- Budgets carry over from 1.6.0 baseline: startup ≤ 1.2 s, working set ≤ 150 MB, idle ~0%.

## 11. Accessibility, resilience, and fallback plan

- Generated XAML views include standard `AutomationProperties.Name` and keyboard focus navigation.
- Templates avoid hardcoded colors/brushes to ensure complete High Contrast and Light/Dark theme compatibility.

## 12. Dependency, license, and security impact

- Zero new runtime package dependencies.
- No secrets in any template.
- All template files licensed under MIT matching project license.

| Risk | Mitigation |
|---|---|
| Template token collision in generated XAML/C# | Use precise `sourceName` and explicit `symbols` configurations |
| Name with special characters / spaces | Test generator script with various names and validate error handling |
| VSIX drift / compatibility issues | Mitigated by adopting CLI-first native integration (ADR-0019) |
