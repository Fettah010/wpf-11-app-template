## 1. Outcome and success definition

The minimal window becomes a polished application frame: `FluentWindow` +
`TitleBar` + `NavigationView` with **rail** (`LeftCompact`) and **sidebar**
(`Left`) modes, back navigation, system/light/dark switching, persisted
shell preferences, and a Mica prototype behind a setting with opaque fallback.
Two pages (Home, Settings) prove navigation, lifecycle, and live settings.

Measurable success: `eng/smoke.ps1` green; app launches to the rail/sidebar
shell, navigates Home↔Settings, survives restart with preferences restored,
theme/backdrop changes apply live; tests ≥8 passing; startup/memory compared
against the 0.1.0 baseline without regression beyond stated bounds.

## 6. Design and architecture

- **Shell contracts:** `ShellMode { Rail, Sidebar }`; `NavigationView.PaneDisplayMode` = `LeftCompact`/`Left`; width<800 → `LeftMinimal` (overlay) regardless of preference, restored on widen. `IsPaneOpen` persisted per mode? No — persisted single `IsPaneOpen`, default true in Sidebar.
- **Navigation:** `INavigationService` + `IPageService` singletons (WPF-UI impls); pages transient, VMs transient except `MainViewModel` singleton; `CacheHistory=0` (no caching; state via VMs/services).
- **Lifecycle:** `INavigableView<T>` on pages; `INavigationAware` on page VMs (`OnNavigatedTo/From` hooks, minimal use: Settings reloads from service on entry).
- **Services:** `ISettingsService.LoadAsync/SaveAsync/Current/UpdateAsync`; `IThemeService.ApplyAsync(ThemeMode)` + `ApplyCurrentAsync`; `IBackdropService.ResolveEffective(bool hc)` pure mapping + `ApplyTo(FluentWindow)`? No — window reads `EffectiveBackdrop` in code-behind (view boundary). Services know nothing of windows (testable, no STA).
- **Startup order:** load settings → build host → apply theme → create window → set chrome/backdrop → `SetNavigationControl` → navigate Home → show.
- **No new assemblies:** pages/VMs/services live in `DevTemWpf.App` (`Views/`, `ViewModels/`, `Services/` folders). Library split needs a second consumer (ADR-0003 holds).

## 11. Accessibility, resilience, and fallback plan

- Nav items expose Content as accessible names; Settings controls labeled; focus-visible via WPF-UI theme; logical tab order (nav → content).
- Backdrop failure/unsupported → None; theme load failure → app still opens (existing startup guard); settings file corrupt → defaults + overwrite (logged to debug, no crash).
- High-contrast: WPF-UI HC dictionaries + forced backdrop None; verified by code path only (cannot enable HC on this machine — limitation).

## 14. Risks and mitigations

| Risk | Mitigation |
|---|---|
| `ExtendsContentIntoTitleBar` + backdrop throws if misordered | Set extend-first in code-behind before backdrop; guard with try + fallback None |
| `SystemThemeWatcher` leaks/double-apply | Watch once per window lifetime; unwatch on close; Changed→persist? No, persist only explicit user choice |
| Settings JSON corrupt | try/catch → defaults; overwrite on next save |
| Scope creep (tokens/gallery/services) | §5 + task→AC mapping; extras → DEFERRED.md |
| No STA tests for nav stack | Smoke launch proves composition; limitation recorded |
