## 1. Outcome and success definition

Production services become individually selectable, safer, better documented,
and more complete for Windows desktop apps. Success = every advertised module
field-service flag has a **file / package / reference / registration /
configuration / output** contract with presence *and* absence checks; Windows
app notifications have a functional optional integration with correct
activation and honest fallback; the update and backup/restore flows handle
failure boundaries with tests; logs stay bounded and private; signing and
distribution claims are separated from real signing; and all existing gates
stay green with no Clean-preset regression.

  preset.
- Conditional inclusion is done with `//#if (IncludeServices)` in C#
  (`AppComposition.cs`, `MainWindow.xaml.cs`, `App.xaml.cs`,
  `NavigationRoutes.cs`) plus `<!--#if ... -->` in the csproj and the
  `templates/support/FEATURES.md` manifest. This is the coarse, inconsistent
  pattern §8.6 asks to replace with derived symbols/templates.
- Update flow (ADR-0011): explicit-only state machine
  (`Disabled/Idle/Checking/Available/UpToDate/Downloading/ReadyToRestart/Failed`)
  over an `IUpdateEngine` abstraction (`VelopackUpdateEngine`) with a
  Stable/Beta channel choice and `StableFeedUrl`/`BetaFeedUrl` options.
- Backup/restore (`BackupService`): BCL zip of `settings.json` + `app.db`
  (+`-wal`/`-shm`) + `versions.txt`; restore validates the presence of
  `settings.json`.
- Logging (`Logging.cs`): Serilog rolling daily files, 14-day retention, no
  redaction or size cap; paths via `AppPaths` under `%APPDATA%`.
- No notifications module, no auth/crash samples, no signing execution; the
  roadmap §4.8 default for Windows App SDK is "optional-only, evidence required".

## 3. Research questions, evidence, and analysis

### 3.1 Windows app notifications (D07t)

| | |
|---|---|
| **Question** | Which notification API, and can an optional module ship without breaking the portable/unpackaged presets? |
| **Options** | (A) `AppNotificationManager` (Windows App SDK `Microsoft.Windows.AppNotifications`); (B) legacy WinRT `ToastNotificationManager` (`Windows.UI.Notifications`); (C) no notifications module |
| **Evidence (2026-10-17)** | MS Learn *Windows notifications overview* — recommended API table: `AppNotificationManager` for "WPF, WinForms, or unpackaged Win32"; `ToastNotificationManager` is "maintenance only", UWP. MS Learn *Use app notifications with a WPF app*: add `Microsoft.WindowsAppSDK`, set `<WindowsPackageType>None</WindowsPackageType>` for unpackaged; register `NotificationInvoked` **before** `Register()`; `Register()` **automatically sets up the COM server** for unpackaged apps; packaged apps need `windows.toastNotificationActivation` + `windows.comServer` manifest extensions with a CLSID. MS Learn *app-notifications-quickstart* (updated 2026-09-10): app notifications are **not supported for elevated (admin) apps** (`Show` fails silently). MS Learn *Deploy unpackaged apps* (2026-05-29): unpackaged Windows App SDK apps need the runtime deployed (installer or MSIX) plus the VC++ redistributable and bootstrapper init. NuGet `Microsoft.WindowsAppSDK`: latest stable **2.5.1** (2026-09-16); 2.0 line since 2026-04-29 under semantic versioning |
| **Finding** | `AppNotificationManager` is the only current path; it works unpackaged (COM registration handled by `Register()`), requires the Windows App SDK runtime on the machine, and silently no-ops when elevated. A packaged/MSIX build needs manifest extensions. This is a real first-party dependency with a per-machine runtime footprint — exactly what roadmap §4.8 says must be proved "optional-only … per enabled/disabled preset" |
| **Decision** | (A) as an **optional Windows-integration module**, gated by a spike (S06/T06): ship only if (a) generation with the module off adds no package/reference/source/registration, (b) module-on generation builds and runs unpackaged, (c) activation routes to the app and the cold-start COM path is exercised, (d) a default in-app fallback exists. Manifest/identity cases that do not work are documented rather than claimed |
| **Validation** | Template presence/absence matrix; launch + activation UI test; documented unsupported cases |

### 3.2 Update experience and distribution (D07s)

| | |
|---|---|
| **Question** | What can the update flow add and prove without owning release servers or signing keys? |
| **Options** | (A) extend the existing explicit `IUpdateEngine` flow using Velopack capabilities; (B) replace Velopack; (C) leave as-is |
| **Evidence (2026-10-17)** | Velopack docs *Integrating overview*, *Switching channels*, *Targeting a specific version*, `UpdateOptions`, `UpdateManager`: `CheckForUpdatesAsync` returns an `UpdateInfo` with version + deltas + release notes; `ExplicitChannel` overrides the built channel; `AllowVersionDowngrade` enables channel switches/lateral moves (auto-apply never downgrades — an explicit apply is required); deltas fall back to full when > `MaximumDeltasBeforeFallback` (default 10), when deltas exceed the full size, or when no local base exists; downloads take a per-app `.velopack_lock` and throw `AcquireLockFailedException` on overlap; `UpdatePendingRestart` reports a downloaded-but-unapplied asset; `WaitExitThenApplyUpdates` waits 60 s then kills. Pinned here: Velopack 1.2.161 (MIT, net10 asset) |
| **Finding** | Channel switching, downgrade/rollback, delta-vs-full, retry, cancellation, and a restart prompt are all supported by the pinned version — the gap is mostly UX, error boundaries, and documentation, not new capability. Real signing is a user-owned secret (no cert here) |
| **Decision** | (A) improve the existing flow: expose current-vs-available version, channel switch with explicit downgrade confirmation, retry, cancel, and restart prompt; consume Velopack's delta/full decision rather than reimplementing it; document that script verification ≠ real signing; keep "unsigned" claims explicit |
| **Validation** | Fake-engine unit tests over each failure boundary; docs review |

### 3.3 Crash reporting and authentication samples (D07r)

| | |
|---|---|
| **Question** | Which optional samples, and how to satisfy "strictly opt-in, no embedded secrets, no default telemetry"? |
| **Options** | Crash: (A) Sentry .NET (`Sentry`, DSN via env var); (B) Azure Monitor / Application Insights (connection string); (C) local-first crash capture with an optional export hook; (D) none. Auth: (A) MSAL (`Microsoft.Identity.Client`) against Entra ID; (B) generic OIDC/OAuth PKCE; (C) none |
| **Evidence (2026-10-17)** | MS Learn *App Center retirement*: Visual Studio App Center retired 2025-03-31 (Analytics & Diagnostics extended to 2026-06-30) → **App Center is excluded**. Sentry docs (2025): WPF/.NET support, DSN discovered via environment variable, explicit PII opt-in, event-sampling controls. `docs/DEFERRED.md` D12: Application Insights is currently a **test-only transitive** and must stay test-only or be removed |
| **Finding** | Both vendors are viable and both are third-party network dependencies; the security posture (env-based config, redaction, opt-in) is the actual requirement, not the vendor |
| **Decision** | Owner decision (§3.5). Recommended: crash = **(C)** local-first capture in the app (no vendor, no telemetry by default) with a documented adapter seam for a user-chosen reporter; auth = **(A)** MSAL sample, strictly opt-in and config-gated, verified for version/license at task start. Either way, D12 stays intact (no App Insights product dependency) |
| **Validation** | Security/privacy review note; "disabled without configuration" tests; secret-leak scan |

### 3.4 Per-service template flags

| | |
|---|---|
| **Question** | How to express per-service flags without inconsistent manual `#if`? |
| **Options** | (A) one `choice` parameter with `allowMultiple` + computed symbols + source modifiers; (B) many `bool` parameters; (C) keep the single `IncludeServices` flag |
| **Evidence (2026-10-17)** | Repo: `docs/template/presets.md` records that the engine substitutes choice *keys*, ignores custom `value`s, and that multi-line `#if` initializers are invalid C# in repo builds (verified 2026-10-14); the current model uses computed symbols + per-file `modifiers[].condition` excludes. `.template.config/template.json` uses `sources[].modifiers` with `condition` for file exclusion |
| **Finding** | The existing modifier mechanism already supports per-file inclusion; what is missing is finer symbols and a manifest that records the *dependency graph*. `allowMultiple` choice parameters need a template-engine capability proof in this repo before relying on them |
| **Decision** | (B) per-module **bool** parameters inside a new `Custom` preset, with the named presets (Clean/Recommended/Full) still computed. Rationale: the template engine's `computed` expressions support only comparisons and `&&`/`||`/`!`/parentheses — no method calls — so an `allowMultiple` choice cannot be reduced to per-module conditions (`Services.Contains(...)` is not expressible). Design: `Preset` gains `Custom`; `Include<Module> = (Preset == "Full") || (Preset == "Recommended") || (Preset == "Custom" && Custom<Module>)` (per documented preset set). All inclusion stays file-level via `sources[].modifiers`; the dependency graph is enforced by a presence/absence matrix test |
| **Validation** | Minimal generation spike; pairwise + named-preset matrix; absence assertions in source and package |
| **Spike result (2026-10-17)** | Minimal throwaway template (Preset Clean/Recommended/Full/`Custom`, `CustomFeatureA` bool, computed `IncludeFeatureA`) generated in isolated hive (`DOTNET_CLI_HOME`). All five cases correct: Recommended→include/ON; Clean→exclude/OFF; Custom (bool=false)→exclude/OFF; Custom (bool=true)→include/ON; Clean+bool=true→exclude/OFF (named preset wins). Confirms `computed` `&&`/`\|\|`/parentheses, bool-parameter parsing, `sources[].modifiers[].condition` file exclusion, and `//#if` text conditionals. Design in §3.4 **adopted**; no `allowMultiple` needed. (First attempt polluted the scratch dir by generating *inside* the template source — recursive nesting; corrected by keeping template and outputs as siblings.) |

## 6. Design and architecture

- **Feature graph first.** A single source of truth (a table in
  `docs/template/presets.md`, mirrored as `--if`-driven rows in the generated
  `FEATURES.md`) lists, per module: files, packages, DI lines, config section,
  resources, runtime/installer requirements, and tests. Every module has an
  explicit inclusion condition; nothing is included implicitly.
- **Flags.** New symbols are computed where possible (`Preset` still drives the
  named presets). Individual module on/off is expressed via a
  `allowMultiple` choice parameter if the T02 spike proves it; otherwise one
  `bool` parameter per module. File-level inclusion uses existing
  `sources[].modifiers` conditions rather than ad-hoc `#if`; C# `#if` remains
  only where a whole line of code must disappear and cannot be file-split.
- **Module contracts (each independently meaningful).** logging, localdata
  (SQLite), http, backup, updates, tray, localization (always on today, but
  documented as a module), diagnostics UI, notifications (new, optional). The
  update engine and tray remain independent of each other; logging stays usable
  by diagnostics when both are on.
- **Notifications module.** `Microsoft.WindowsAppSDK` (`WindowsPackageType=None`
  for unpackaged), a thin `INotificationService` adapter with a no-op/in-app
  fallback, `Register()`/`NotificationInvoked` wired at startup **only when the
  module is enabled**, activation arguments parsed into a route, and a
  documented "unsupported" result for elevated/packaged-without-manifest cases.
  App notifications never become a startup requirement.
- **Update UX.** Extend `IUpdateEngine`/`UpdateService` with: available-vs-current
  version, channel switch (Velopack `ExplicitChannel` + `AllowVersionDowngrade`
  with explicit confirmation), retry, cancel, restart prompt, and consumption of
  Velopack's delta/full decision; each failure maps to a user-visible status
  (existing state machine), never a crash.
- **Backup/restore.** Add a validated restore path: reject absolute/traversal
  entry names, bound entry size/count, verify `versions.txt` schema/version,
  atomically replace via temp + move, and keep "restore-to-new-location" a
  supported, tested operation. Corrupt/unsupported input returns a typed failure.
- **Logging.** Json/structured-safe rendering, redaction of known secret-shaped
  values, a documented retention/size policy enforced in `Logging.cs` +
  `AppPaths`, and all files under `%APPDATA%`.
- **Samples security posture.** Auth/crash samples are excluded unless
  explicitly selected; configuration comes from environment/appsettings with
  empty-by-default values; no secrets in source, logs, or the template; crash
  payloads are redacted and off unless a DSN/connection string is supplied.
- **Compatibility.** `ShellSettings` stays additive; no persisted value changes.
  Presets keep their documented sets (Clean minimal; Recommended adds
  diagnostics + services; Full adds dashboard). New module flags add finer
  control without changing the named presets' meaning.
- **ADR.** ADR-0017 "Per-service modules, Windows integration, and optional
  samples" records the flag model, the notifications go/no-go, the samples
  posture, and the App Center exclusion.

- Reference: proxy machine (MSI MS-7E28, Ryzen 8700G, 32 GB, 2560×1440, build

  default/Recommended app; idle ~0%; Clean must not regress vs 1.5.0. Adding the
  notifications module must not change startup when the module is off, and must
  stay within budget when on. Fallback expectation: module-off metrics match the
  1.5.0 baseline within noise.

## 11. Accessibility, resilience, and fallback plan

- Keyboard/focus/automation names preserved; update/notification surfaces fully
  keyboard-operable; status text announced.
- Notifications degrade to an in-app (snackbar) fallback; failure never blocks
  startup or navigation.
- Update/backup failures surface as typed status, never exceptions escaping to
  the UI thread; cancellation honored; partial writes avoided.
- Samples default to disabled/no-op with zero network activity.
- Settings remain additive and backward-compatible.

## 12. Dependency, license, and security impact

## 14. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Per-service flags explode the matrix | Named presets + pairwise coverage; explicit absence asserts; no full power set |
| Notifications need a per-machine runtime | Optional-only module; spike go/no-go; in-app fallback; document unsupported modes |
| Windows App SDK changes startup/footprint | Measure per preset; module off ⇒ no package/reference/registration |
