Prove the independently consumable token-resource boundary, explicitly reject unproven Windows/service splits, and define the 1.x compatibility surface before starting the breaking 2.0 conversion.

## 3. Research questions, evidence, and analysis

### 3.1 Assembly boundary candidates (DevTemWpf.UI / DevTemWpf.Windows / services)

| **Question** | Which types belong in which assembly, and what is each boundary's demonstrable second consumer? |
|---|---|
| **Options** | (A) Keep one app (status quo, ADR-0003); (B) UI library + Windows layer + service modules + app shell; (C) UI-resource library only; keep shell, Windows integration, motion, and services in the app |
| **Evidence** | ADR-0003 revisit trigger: "Second consumer for shared XAML/services, or TFM friction on clean machines." WPF-UI 4.3.0's project targets `net10.0-windows` and references `Wpf.Ui.Abstractions`; Microsoft documents pack URIs for resources compiled into referenced assemblies and notes that static resource references suit resource dictionaries compiled into shared DLLs. Sources: [WPF-UI 4.3.0 project](https://github.com/lepoco/wpfui/blob/4.3.0/src/Wpf.Ui/Wpf.Ui.csproj), [WPF pack URIs](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/app-development/pack-uris-in-wpf), [XAML resources overview](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/systems/xaml-resources-overview). Verified 2026-10-28. |
| **Finding** | The built `DevTemWpf.UI` package has now been consumed by an independent WPF canary with no gallery or project reference; this proves the token-resource boundary technically. It does not justify moving app-owned motion, shell chrome, Windows APIs, or service implementations: those have no second consumer and are coupled to `MainWindow`, `ISettingsService`, `ShellSettings`, WPF-UI, and the existing per-module template flags. |
| **Decision** | Accept only the UI resource boundary for the 1.8 architecture proof. Keep `DevTemWpf.Windows` and service assemblies as no-go absent a second consumer; record both the accepted UI boundary and the rejected speculative splits in ADR-0020. |

### 3.2 Resource/theme resolution across assembly boundaries

| **Question** | How do `DesignTokens/` dictionaries, pack URIs, and WPF-UI merged dictionaries resolve when UI assets live in a separate library? |
|---|---|
| **Options** | (A) ComponentResourceKey / pack URI to library; (B) StaticResource with Source="pack://..."; (C) Keep tokens in app, library exposes only controls |
| **Evidence** | The app merges WPF-UI theme/control dictionaries before library token resources. The app integration suite and a clean package-only consumer both resolve the referenced-assembly pack URIs; both verify the density dictionary swap (`AppPageMargin` 24 → 16). Sources: [WPF pack URIs](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/app-development/pack-uris-in-wpf) and [XAML resources overview](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/systems/xaml-resources-overview), verified 2026-10-28. |
| **Finding** | The original app-relative density URI did not identify a referenced-assembly resource. The documented pack URI works in the app and from the built package; the app remains composition root and owns the active density choice. No custom controls or design-time-only library surfaces are introduced. |
| **Decision** | Prototype a library-owned dictionary merged by the consumer using the documented referenced-assembly pack URI form; do not assume the current relative `DesignTokens/Spacing.*.xaml` URI works unchanged after moving the dictionary. |

### 3.3 1.x-to-2.0 compatibility surface

| **Question** | Which 1.x surfaces are public contract vs. internal vs. gallery-only, and what is the 2.0 state of each? |
|---|---|
| **Options** | (A) Full inventory + per-item classification; (B) Ad-hoc mapping |
| **Evidence** | §14.2 requires an inventory of public APIs, resource keys, template parameters, generator output, package references, DI conventions, configuration/settings formats, and distribution paths, each mapped to preserved/renamed/moved/replaced/deprecated/removed. |
| **Finding** | Only (A) satisfies §14.2; it feeds the migration draft and ADR. |
| **Decision** | Produce the compatibility inventory as part of the plan's research output (table below), then a migration draft covering the UI resource move and explicitly retained app-level contracts. |

### 3.4 Downstream canary proof

| **Question** | Can a clean consumer app build and launch using the built library packages with zero gallery reference? |
|---|---|
| **Options** | (A) Project-reference only (insufficient per §8.8); (B) Built `.nupkg` consumed from clean temp repo |
| **Evidence** | §8.8 requires a clean consumer of built packages. `eng/test-ui-package.ps1` packs `DevTemWpf.UI`, restores a copied WPF app from the local package feed plus NuGet, builds with warnings as errors, checks Comfortable and Compact tokens, and launches it without a project reference to the gallery. The source/package template matrix separately exercises generated Clean/Recommended/Full consumers. |
| **Decision** | Keep the package-only UI canary and run the complete generated-app matrix against source and the 1.8 template package. Do not invent a full services-package consumer because service assemblies are not justified. |

### 3.5 Hosted, delayed release execution

| **Question** | How can the v1.8 release run about 12 hours later without the user's PC, while preventing an unverified or wrong commit from being published? |
|---|---|
| **Options** | (A) Local scheduled task or always-on machine; (B) GitHub-hosted Actions schedule; (C) publish immediately without a final gate |
| **Evidence** | GitHub documents `schedule` as UTC cron, requires the workflow file on the default branch, and warns scheduled events can be delayed during high load. GitHub-hosted Windows runners can execute the repository's WPF gates; `GITHUB_TOKEN` permissions can be restricted per job. Sources: [schedule event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule), [GITHUB_TOKEN permissions](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token#permissions-for-the-github_token), accessed 2026-10-28. |
| **Finding** | Option B satisfies the no-PC requirement, but a schedule is best-effort, not a hard real-time guarantee. Scheduling at 08:09 UTC avoids the top-of-hour contention described by GitHub; date guard, exact SHA pin, final gates, idempotency check, and failure-without-publication are required. |
| **Decision** | Use a one-date GitHub Actions schedule for 2026-10-29 08:09 UTC on the default branch. After the 1.8 merge, the workflow's push-triggered preflight reruns the gates and creates `v1.8.0-candidate` at that exact successful commit. The scheduled job checks out that pinned candidate commit, reruns build/test/UI/generator/template/package/audit gates, and publishes `v1.8.0` only after all pass. If it is late, skipped, or fails, leave the release unpublished and report the limitation. |

### Boundary choice and current prototype

The baseline app has no reusable custom control classes (`Control`, `ContentControl`, or `UserControl` subclasses) in `src/DevTemWpf.App`; the custom-control implementation exists only as an item-template example. At baseline, `App.xaml` loaded WPF-UI's theme/control dictionaries before app-owned design tokens, and `DesignTokenBootstrap` used app-relative URIs. The prototype moves only token dictionaries into `DevTemWpf.UI` and verifies runtime pack-URI loading and density switching. `MotionService` still directly consumes app-owned `ISettingsService`/`ShellSettings` and WPF-UI state. Do not move motion or invent a `Generic.xaml` control layer until a decoupled contract and a real second consumer are demonstrated.

## 6. Design and architecture

- `DevTemWpf.App` composes the accepted `DevTemWpf.UI` resource library. The generated template includes the source library project and app project reference; the separate canary consumes the packed package, not the gallery project.
- `DevTemWpf.UI`: owns only token dictionaries (`DesignTokens/`) in this proof; runtime pack-URI loading, density replacement, and a package-only consumer are verified. No reusable app controls currently exist, so do not add `Themes/Generic.xaml` or speculative controls to this slice.
- Motion remains in the app for the first slice: `MotionService` consumes persisted shell settings and app-owned interfaces. Revisit only after defining and testing a library-level policy boundary that does not make the UI package depend on the gallery/app.
- Keep `MainWindow`, backdrop, tray, notifications, motion, `AppComposition`, and optional service implementations in `DevTemWpf.App`; per-module template flags already remove optional source, references, registrations, and behavior.
- Do not create `DevTemWpf.Windows` or `DevTemWpf.Services.*` projects without an independent consumer and an accepted boundary decision.
- Dependency direction: `DevTemWpf.App` → `DevTemWpf.UI` → WPF-UI resources; app-owned Windows/services remain composed by `AppComposition`.
- Resource keys: app-owned `StaticResource` token keys (`AppPageMargin`, etc.) resolve from UI library via pack URI / `ComponentResourceKey`; app `App.xaml` remains composition root.
- Navigation: `NavigationRoutes` registry pattern preserved; page `Type` identities stay in app shell.

## 14. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Speculative abstraction (library with one consumer) | The token-only package has an independent package canary; explicitly reject Windows/service splits until each has a real second consumer |
| Pack URI/theme resolution failures across assemblies | Verify in canary `App.xaml`; fall back to app-owned tokens if unresolved |
| Design-time XAML breakage in VS | Compile the library and generated app XAML, run the downstream consumer, and avoid designer-only markup or custom controls; record that Visual Studio designer interaction is not automated |
| Performance regression from split | Measure; revert boundary granularity if overhead is pointless |
| Scheduled event is delayed or not run | Run at 08:09 UTC rather than on the hour; use a date guard, pinned commit, blocking gates and no-publication-on-failure; GitHub scheduling is best-effort, not a deadline guarantee |
