## 1. Outcome and success definition

The Tabbed shell's document area renders with the correct theme surface — no
pure-white panel — on both dark and light themes, and the detail splitter uses
the themed divider color instead of the bright default. Success = the defect
is fixed at the root, a regression test fails on the pre-fix revision and
passes after, visual verification can detect a white-surface regression
mechanically, README content + visuals reflect the fixed shell, and `v1.4.1`
ships as an untouched-line patch over `v1.4.0`.

## 6. Design and architecture

- `src/DevTemWpf.App/Views/WorkspacePage.xaml`:
  - `ui:TabView` gains `Style="{StaticResource {x:Type TabControl}}"` so the
    WPF-UI `TabControl` style (transparent `TabViewBackground`, `CornerRadius
    0,4,4,4`, top border) is applied to the derived control. Tab item headers
    are already WPF-UI-styled (WPF-UI's `TabView` creates base `TabItem`
    containers, which match the `Style TargetType="TabItem"` exactly).
  - `GridSplitter` gains `Background="{DynamicResource AppDividerBrush}"`.
  - `Frame` remains `Background="Transparent"` (original intent: the document
    surface is the host layer `#272727`).
- Token rule respected: `AppDividerBrush` already exists in
  `DesignTokens/SemanticColors.xaml`; no WPF-UI key is redefined and no new
  raw WPF-UI key is referenced inline.
- No change to `ui:TabViewItem` (containers are base `TabItem`, already themed).
- Documented consequence: the document area and chrome share the same
  `#272727` layer (consistent with all other shells, whose pages also render on
  the NavigationView host). Recorded in the report with the measured evidence.

## 9. Test and CI plan (explicit UI execution / visual / template matrix gates)

- Unchanged required gates: Release build `--warnaserror --no-incremental`,
  full suite with recorded counts, `eng/check-ui-tests.ps1` (executed > 0, zero
  skips), `eng/smoke.ps1`, both template matrices, vuln/deprecated audits,
  remote trio green before merge.
- New regression test (T03): an STA/XAML test that loads the app resource
  dictionaries and the `WorkspacePage` definition (or applies the same style
  resolution) and asserts the `ui:TabView` resolves the WPF-UI `TabControl`
  style whose background is the transparent theme brush — i.e. the derived
  control is themed, not the built-in white template. (Exact mechanism chosen
  at implementation to be deterministic and CI-safe; the required property is
  "red on the reverted fix, green on the fix".)
- Visual verification (T04): a deterministic capture (PrintWindow, not
  `CopyFromScreen`, to avoid unpainted frames) of the maximized Tabbed shell
  whose pixel check asserts (a) pure-`#FFFFFF` fraction below a small
  threshold in Dark, and (b) the document surface equals the expected themed
  color; plus the splitter-color check. Integrated so the gate fails on a
  white-surface regression. Thresholds and any mask are documented, not hidden.
- README captures (T05): recapture with recorded provenance (Windows build /
  scale / theme / capture method), baseline discipline unchanged (deliberate
  human-reviewed updates only).
- Template matrix: unchanged from 1.4.0; run both matrices to confirm the
  patch does not regress generation/build/launch.

## 14. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Fix hides a deeper layer problem (surface chosen by eye) | Root cause proven by A/B; color invariants measured, not eyeballed |
| `{StaticResource {x:Type TabControl}}` resolves only at parse time and breaks if WPF-UI changes | Launch/UI gate catches it; documented fallback token surface |
| Visual check flaky across machines (fonts/AA) | Check targets large solid regions + token colors, not text; deterministic PrintWindow capture; thresholds documented |
| README recapture drifts from pinned environment | Record provenance; deliberate review; never auto-approve baselines |
